## 0. 본 문서 범위

설계 산출물을 작성한다. 작성한 DESIGN.md가 UI 설계와 클래스/시퀀스 다이어그램에 집중했다면, 그 상위의 아키텍처 스타일 선정과 설계 원리 적용 근거를 다룬다.


## 1. 아키텍처 기초 

시스템을 두 개의 서브시스템(모듈)으로 분할한다.

- **Presentation 서브시스템** (`app.py`): 사용자 입력 수집과 결과 표시. Streamlit 위젯으로 구성.
- **Domain 서브시스템** (`orderbook.py`): 주문 매칭이라는 핵심 비즈니스 로직. `OrderBook`, `Order`, `Trade`로 구성.

두 서브시스템은 함수 호출 인터페이스(`submit_order`/`cancel_order`/`get_book`/`get_trades`)로만 상호작용한다.

## 2. 아키텍처 스타일 선정 

### 2.1 후보 비교

강의록의 주요 스타일 중 본 시스템에 적용 가능한 후보를 평가했다.

| 스타일 | 적합성 | 판단 |
|---|---|---|
| **계층형 (Layered)** | ★★★ | UI와 도메인 로직의 명확한 수직 분리에 부합 → **채택** |
| MVC | ★★☆ | 계층형 위에 역할 매핑으로 보조 적용 (View/Controller/Model) |
| 이벤트 기반 | ★☆☆ | 단일 사용자·동기 처리라 이벤트 버스 도입은 과설계 |
| 파이프-필터 | ☆☆☆ | 데이터 변환 파이프라인이 아니므로 부적합 |
| 클라이언트-서버 | ☆☆☆ | 네트워크 분산이 없는 단일 프로세스라 불필요 |

### 2.2 계층형 채택 근거

계층형의 장점이 본 시스템 목표와 정확히 일치한다.

- **추상화·캡슐화**: UI는 매칭 알고리즘의 내부를 몰라도 된다.
- **높은 응집**: 매칭 로직이 Domain 층 한 곳에 모인다.
- **재사용**: 동일 엔진을 CLI·테스트·다른 UI에서 재사용 가능 (실제로 `test_orderbook.py`가 UI 없이 엔진만 재사용해 검증).

### 2.3 MVC 관점 매핑

계층형 위에 MVC 역할을 매핑하면 책임이 더 분명해진다.

| MVC 역할 | 본 시스템 대응 |
|---|---|
| **Model** | `OrderBook`, `Order`, `Trade` — 상태와 매칭 규칙 |
| **View** | Streamlit 위젯 렌더링 (호가창 테이블, 체결내역) |
| **Controller** | `app.py`의 버튼 이벤트 핸들러 — 입력을 받아 Model 메서드 호출 |

## 3. 전통적 설계 원리 적용

| 원리 | 적용 내용 |
|---|---|
| **추상화** | `OrderBook`이 가격-시간 우선 매칭의 복잡성을 4개 public 메서드 뒤로 추상화 |
| **캡슐화 / 정보 은닉** | `_bids`/`_asks`/`_trades`는 비공개. 외부는 `get_book()`/`get_trades()`로만 접근하며, 이들은 **방어적 복사**(`list(...)`)를 반환해 내부 상태 변조를 차단 |
| **모듈화** | 도메인(`orderbook.py`)과 표현(`app.py`)을 별도 모듈로 분할 |

## 4. 객체지향 설계 원리 적용

| 원리 | 적용 내용 |
|---|---|
| **SRP (단일 책임)** | `Order`/`Trade`는 데이터만, `OrderBook`은 매칭만, `app.py`는 표현만 담당. 엔진 내부도 `_match`/`_record_trade`/`_insert_into_book`/`_is_matchable`/`_validate_order_input`로 책임을 분리 |
| **OCP (개방-폐쇄)** | 현재는 지정가 주문 단일 타입. 주문 타입 확장은 §6의 전략 패턴으로 대응 예정 (기존 코드 수정 없이 확장) |
| **DIP (의존 관계 역전)** | `app.py`(구체적 UI)가 `OrderBook`의 **안정적인 public 인터페이스**에 의존하고 내부 구현에는 의존하지 않음. 강의록의 "구체화된 모듈이 추상화된 모듈에 의존하도록 역전" 원리 적용 |

> 약결합 사례: `Trade`는 `Order` 객체를 직접 참조하지 않고 `buy_order_id`/`sell_order_id`(ID)만 보관 → 순환 참조 제거.

## 5. 설계 메트릭 관점 

정량 측정은 품질 문서에서 수행하고, 여기서는 아키텍처 수준의 정성 평가만 기록한다.

- **결합도 (Coupling)**: 낮음. 모듈 간 의존이 단방향(Presentation → Domain)이며 함수 시그니처로만 연결.
- **응집도 (Cohesion)**: 높음. `OrderBook`의 모든 메서드가 "주문 매칭"이라는 단일 목적에 기여(기능적 응집).
- **복잡도**: 낮음. 분기 깊이가 얕고(`_match` 루프 1중첩), 매직 넘버 없음.

## 6. 디자인 패턴 

### 6.1 현재 적용

본 시스템은 소규모라 무거운 GoF 패턴을 도입하지 않았다. `@dataclass`로 데이터 보관 보일러플레이트를 제거한 정도가 전부다. 패턴을 위한 패턴은 과설계라는 판단에 따른 의도적 결정이다.

### 6.2 향후 적용 후보 — 전략 패턴 

주문 타입을 다양화(지정가·시장가·IOC 등)할 경우, 각 매칭 정책을 전략(Strategy)으로 캡슐화하면 `OrderBook` 수정 없이 주문 타입을 추가할 수 있다(OCP). 현재는 YAGNI 원칙으로 미적용하고 확장 지점만 명시한다.

## 7. 아키텍처 평가 

강의록의 ATAM(여러 품질 속성에 초점)을 적용해 핵심 품질 속성별로 평가한다.

| 품질 속성 | 시나리오 | 아키텍처 결정 | 평가 |
|---|---|---|---|
| **테스트성** | 엔진 로직을 UI 없이 검증 | 도메인-표현 계층 분리 | 좋다 — `test_orderbook.py` 24개가 UI 없이 통과 |
| **수정 용이성** | UI 색상/배치 변경이 매칭 로직에 영향 없어야 함 | 계층 분리 + 단방향 의존 | 괜찮다 — `app.py`만 수정하면 됨 |
| **성능** | 호가가 많을 때 주문 삽입 비용 | 정렬된 list 삽입 = O(n) | 상충 효과 있음 — heap(O(log n)) 대비 느리나, 학습용 소규모라 단순성을 우선 (DESIGN.md §6) |
| **학습성** | 처음 사용자가 5분 내 첫 주문 | 샘플 주입 버튼 + 즉각 피드백 | 만족 |

- **민감점(Sensitivity Point)**: 매칭 정확성은 `_insert_into_book`의 정렬 불변식(가격·시간 순)에 민감 → 테스트로 집중 검증(가격우선·시간우선 케이스).
- **트레이드오프 지점(Tradeoff Point)**: 자료구조 선택(list vs heap)에서 **단순성 ↔ 성능**이 충돌. 시스템 목표(학습성)에 따라 단순성을 선택.
