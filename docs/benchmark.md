# 성능 벤치마크 — list vs heap (List vs Heap Benchmark)

**관련 문서**: [architecture.md](./architecture.md), [SRS.md](./SRS.md) (NFR-P-01·P-02), [quality.md](./quality.md)


---

## 0. 본 문서의 목적

아키텍처 단계에서 호가창 자료구조로 **list**를 선택하면서, "단순성을 위해 list를 쓰며, 이 규모에서는 성능이 충분하다"고 ATAM 평가에 적었다. 본 문서는 그 주장을 **말이 아니라 실제 측정값**으로 뒷받침한다. 같은 시나리오를 list 기반(현재 구현)과 heap 기반(대안)으로 돌려, 호가 수가 늘 때 주문당 처리 시간이 어떻게 변하는지 비교했다.

---

## 1. 측정 방법

- **시나리오**: 호가창에 미체결 주문 N개를 쌓아 둔 상태에서, 주문 1건을 처리하는 데 걸리는 평균 시간(µs)을 측정.
- **N 값**: 100, 500, 1,000, 2,000, 5,000 (NFR-P-02의 "≥ 1,000건"을 포함·초과).
- **측정 도구**: Python `time.perf_counter`, 각 조건 5회 측정 후 중앙값.
- **비교 대상**: 현재 list 기반 `OrderBook` vs 동일 동작의 heap 기반 최소 구현.

---

## 2. 측정 결과

| 호가 수 N | list 기반 (µs/주문) | heap 기반 (µs/주문) |
|---:|---:|---:|
| 100 | 49.31 | 2.97 |
| 500 | 159.85 | 0.50 |
| 1,000 | 267.54 | 0.41 |
| 2,000 | 447.29 | 0.58 |
| 5,000 | 1083.25 | 0.45 |

![list vs heap 처리 시간](../산출물/benchmark 성능.PNG)

해석:
- list 기반은 호가가 늘수록 주문당 시간이 **함께 증가**한다. 매 주문마다 반대편 호가를 정렬·스캔하기 때문이다.
- heap 기반은 N과 거의 무관하게 **1µs 안팎으로 평평**하다. 삽입·조회가 O(log n)이라 그렇다.

---

## 3. NFR 충족 확인

| NFR | 기준 | 측정 결과 | 충족 |
|---|---|---|---|
| NFR-P-01 | 단일 주문 처리 ≤ 100ms (= 100,000µs) | N=1,000에서 267.54µs ≈ **0.268ms** | ✅ (기준의 약 1/374) |
| NFR-P-02 | 미체결 주문 ≥ 1,000건 보관 | N=5,000까지 정상 처리 | ✅ |

핵심: SRS가 정한 최대 호가 수(1,000건)에서도 list 구현의 주문당 시간은 **기준 100ms의 약 374분의 1** 수준이다. 따라서 "이 규모에서는 list로 충분하다"는 아키텍처의 ATAM 주장은 실측으로 입증된다.

---

## 4. 트레이드오프 결론

heap이 큰 규모에서 더 빠른 것은 사실이다(그래프의 두 선 차이). 그러나:
- 본 시스템의 요구 규모(≤ 1,000건)에서 list는 이미 기준을 수백 배 여유로 만족한다.
- list는 코드가 단순해 읽기·디버깅·취소(임의 위치 제거)가 쉽다. heap은 임의 원소 취소가 까다롭다(요구 단계에서 AI가 heap을 제안했다가 취소와 충돌한 문제와 같은 맥락).

→ **결론: 지금 규모에서는 단순한 list가 합리적 선택이다. 만약 호가 수가 수만 건 이상으로 커지면 heap(또는 가격별 버킷) 도입을 검토한다.** 이 판단 기준(언제 바꿀지)을 숫자로 남긴 것이 본 벤치마크의 성과다.
