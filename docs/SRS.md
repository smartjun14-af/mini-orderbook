# Software Requirements Specification (SRS)

**프로젝트**: Mini-OrderBook  
**버전**: 0.1 (Draft)  
**작성일**: 2026-05-26  
**작성자**: 김동준

## 1. 소개

### 1.1 목적
본 문서는 Mini-OrderBook(미니 호가창/매칭 엔진 시뮬레이터)의 
기능적·비기능적 요구사항을 정의한다. 

본 시스템은 단일 종목에 대한 지정가 주문 접수, 가격-시간 우선 매칭, 
부분 체결, 주문 취소, 호가창 조회 기능을 제공한다.

### 1.2 범위

#### 포함 (In-Scope)
- 단일 종목의 지정가(Limit) 주문 처리
- 가격-시간 우선(Price-Time Priority) 매칭 엔진
- 부분 체결(Partial Fill) 처리
- 주문 취소
- 호가창(Order Book) 조회
- 체결 내역(Trade History) 조회

#### 제외 (Out-of-Scope)
- 시장가(Market) 주문
- 다종목 거래
- 사용자 계정 및 인증
- 실시간 가격 차트
- 데이터 영속성 (DB는 메모리 또는 SQLite로 한정)
- 외부 시스템 연동

## 3. 기능 요구사항

### 3.1 User Stories

**US-01: 매수 주문 제출**  
가격과 수량을 지정해 매수 주문을 제출하고 싶다,
왜냐하면 내가 원하는 조건의 거래만 체결되기를 원하기 때문이다.

**US-02: 매도 주문 제출**  
가격과 수량을 지정해 매도 주문을 제출하고 싶다,
왜냐하면 내가 원하는 가격 이상에서만 매도되기를 원하기 때문이다.

**US-03: 자동 매칭**  
나는 매수가가 매도가 이상일 때 주문이 자동 매칭되기를 원한다,
왜냐하면 그것이 실제 거래소의 작동 방식이기 때문이다.*

**US-04: 부분 체결 처리**  
나는 매칭 가능한 반대편 수량이 부족할 때 일부만 체결되고
잔량이 호가창에 남기를 원한다, 왜냐하면 실제 시장에서 부분 체결이 빈번하기 때문이다.

**US-05: 호가창 조회**  
나는 현재 미체결된 매수·매도 주문 목록을 실시간으로 확인하고 싶다,
왜냐하면 시장 깊이(market depth)를 직관적으로 이해하고 싶기 때문이다.

**US-06: 체결 내역 조회**  
나는 지금까지 체결된 거래 목록을 시간순으로 확인하고 싶다,
왜냐하면 매칭 엔진이 의도대로 작동하는지 검증하기 위해서다.

**US-07: 주문 취소**  
나는 미체결된 내 주문을 취소할 수 있어야 한다,
왜냐하면 마음이 바뀌거나 시장 상황이 변할 수 있기 때문이다.

### 3.2 기능 명세 (Functional Requirements)

**ID/ 요구사항/ 관련 US**

FR-01: 시스템은 매수/매도 지정가 주문을 접수하고 고유 주문 ID를 할당해야 한다 (US-01, US-02)
FR-02: 시스템은 매수가 ≥ 최우선 매도가일 때 자동으로 매칭을 수행해야 한다 (US-03)
FR-03: 시스템은 동일 가격에서 먼저 접수된 주문을 우선 매칭해야 한다 (US-03)
FR-04: 시스템은 부분 체결 시 잔량을 호가창에 유지해야 한다 (US-04)
FR-05: 시스템은 현재 호가창을 가격순으로 정렬해 반환해야 한다 (매수: 내림차순, 매도: 오름차순)/(US-05)
FR-06: 시스템은 체결 내역을 시간순으로 저장하고 조회 가능해야 한다 (US-06)
FR-07: 시스템은 미체결 주문의 취소를 허용하고, 호가창에서 제거해야 한다 (US-07)
FR-08: 시스템은 이미 체결되거나 취소된 주문에 대한 취소 요청을 거부해야 한다 (US-07)


## 4. 비기능 요구사항

### 4.1 성능 (Performance)
- **NFR-P-01**: 단일 주문 매칭 처리 시간은 100ms 이내여야 한다.
- **NFR-P-02**: 호가창에 동시 보관 가능한 미체결 주문은 최소 100건 이상이어야 한다.
- **NFR-P-03**: UI는 주문 제출 후 1초 이내에 호가창 변화를 반영해야 한다.

### 4.2 신뢰성 (Reliability)
- **NFR-R-01**: 매칭 결과는 가격-시간 우선 원칙을 100% 준수해야 한다.
- **NFR-R-02**: 부분 체결 시 체결 수량 + 잔량 = 원 주문 수량을 항상 만족해야 한다.
- **NFR-R-03**: 시스템은 잘못된 입력(음수 가격, 0 수량 등)에 대해 적절한 오류를 반환해야 한다.

### 4.3 사용성 (Usability)
- **NFR-U-01**: UI는 매수(빨강)·매도(파랑) 시각적 구분을 제공해야 한다.
- **NFR-U-02**: 주문 제출 양식은 5초 이내에 완료 가능해야 한다.
- **NFR-U-03**: 호가창과 체결 내역은 동일 화면에서 동시 조회 가능해야 한다.

### 4.4 테스트가능성 (Testability)
- **NFR-T-01**: 매칭 엔진 코어 모듈의 단위 테스트 라인 커버리지는 70% 이상이어야 한다.
- **NFR-T-02**: 모든 user story에 대응하는 통합 테스트 시나리오가 존재해야 한다.
- **NFR-T-03**: 상태 기반 테스트를 통해 주문 상태 전이가 모두 검증되어야 한다.

### 4.5 유지보수성 (Maintainability)
- **NFR-M-01**: 모든 모듈은 PEP8 코딩 표준을 준수해야 한다.
- **NFR-M-02**: 매칭 엔진 코어와 UI/API 레이어는 분리되어 독립적으로 교체 가능해야 한다.
- **NFR-M-03**: 함수당 사이클로매틱 복잡도는 10 이하를 유지해야 한다.

- **개발 언어**: Python 3.11+

- **UI 프레임워크**: Streamlit
- **데이터 저장**: 인메모리 자료구조 (옵션: SQLite)
