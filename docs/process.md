## 1. 프로세스 모델 후보 검토 


| 모델 | 특징 | 본 프로젝트 적합성 |
|---|---|---|
| 폭포수 | 단계 순차, 단계 간 중복 없음 | 단계는 명확하지만 반복이 안 되는 게 비현실적 |
| V-모델 | 폭포수 확장, 각 개발 단계에 대응하는 검증(테스트) 강조 | ◎ 테스트 비중이 높은 이 프로젝트에 맞음 |
| 프로토타이핑 | 시제품으로 요구 확정 | 요구가 이미 명확(학습용)이라 과함 |
| 나선형 | 위험 분석 중심 반복 | 위험 요소 적은 소규모엔 과중 |
| 진화적 | 점증적 기능 확장 | 일부 반복은 가져옴 |
| 애자일 | 짧은 주기, 문서보다 동작 SW | 바이브코딩과 성향은 맞지만, 과제가 문서 산출물을 요구해서 정면으로 부딪힘 |

## 2. 선택한 모델과 근거

### 2.1 선택: **V-모델 기반 + 경량 반복(controlled iteration)**

V-모델을 골격으로 삼되, 뒤 단계에서 결함·빈틈이 나오면 앞 산출물을 제한적으로 고치는 경량 반복을 허용했다.

```
   요구 분석 ───────────────────────────── 인수/시스템 검증
   (SRS)          \                      /   (사용성 계획)
                   \                    /
    아키텍처 설계 ───────────── 통합 테스트
    (architecture)      \          /    (Integration tests)
                         \        /
     상세/UI 설계 ──────── 단위 테스트
     (Design)          \      /        (Unit tests)
                        \    /
                       구현 (coding / orderbook.py)
```

### 2.2 선택 근거

1. **검증을 강조하는게 이 프로젝트랑 맞는다.** V-모델은 각 개발 단계(요구/설계/구현)에 대응하는 검증 단계(인수/통합/단위 테스트)를 명시한다. 이 프로젝트는 커버리지 100%·기법별 분류로 검증에 비중을 크게 뒀으니 V-모델의 좌우 대칭 구조와 잘 맞는다.
2. **단계 경계가 명확해서 산출물 추적이 쉽다.** 각 단계가 분명히 끝나고 베이스라인 산출물을 남기니까(형상관리, maintenance.md), 평가자가 프로세스 적용을 따라가기 좋다.
3. **순수 폭포수의 경직성은 피한다.** 실제로 Design.md를 0.1→0.2로 보강하고, 커버리지 빈틈을 발견한 뒤 테스트를 추가하고, 시장가·IOC·FOK 주문을 뒤늦은 요구로 받아 전략 패턴으로 더한 것 모두 반복이 있었다는 뜻이다. 이걸 부정하지 않고 "경량 반복"으로 모델에 포함시켰다.

## 4. 바이브코딩과 프로세스의 결합 방식

각 V-모델 단계에서 AI와 사람이 역할을 어떻게 나눴는지 정리하면 다음과 같다.

| 단계 | AI 주도 | 사람 주도 |
|---|---|---|
| 요구 | 초안 생성, 누락 점검 | 도메인 정의, 우선순위 결정 |
| 설계 | 다이어그램 형식 변환 | 비자명한 시나리오 명세 |
| 구현 | 코드 생성, 리팩토링 | 설계 적합성 판단 |
| 테스트 | 케이스 생성 | 기법 선택·도메인 유추 |
| 품질 | 메트릭 계산 | 임계값 해석·개선 우선순위 |

각 단계의 산출물을 **다음 단계의 프롬프트 앵커**로 썼다. SRS→설계 프롬프트, 설계→코드 프롬프트로 이어서 일관성을 잡았다.
