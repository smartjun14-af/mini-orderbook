## 0. 본 문서의 범위

본 문서는 V-모델의 마지막 단계인 **품질 관리**에 해당한다. 앞 단계에서 만든 산출물(요구·설계·코드·테스트)을 **품질 속성**과 **품질 메트릭**으로 평가하고, 이를 근거로 본 과제의 주제인 **"프로세스에 입각한 바이브코딩의 효과"**를 정량적으로 결론짓는다. 

여기서 사용하는 모든 메트릭은 추정값이 아니라, 최종 코드(`orderbook.py`)에 대해 `radon`과 `pytest --cov`로 **직접 측정한 값**이며, `measure_metrics.py` 한 번으로 모두 재현된다.

| 채택 | 근거 |
|---|---|
| ISO/IEC 9126 | 강의록이 기준 모델로 다루며, 6개 특성(기능성·신뢰성·사용용이성·효율성·유지보수성·이식성)이 소규모 학습 시스템에도 빠짐없이 대응되어 누락 없는 점검표가 된다. |

## 2. 품질 속성 평가 (정성 평가)

ISO/IEC 9126의 6대 특성을 기준으로, 각 특성을 어떤 산출물·결정으로 만족시켰는지 정리한다.

| 품질 특성 | 본 시스템에서의 실현 | 근거 산출물 |
|---|---|---|
| **기능성** (정확성) | 체결가가 "호가창에 먼저 있던 주문(수동 주문)의 가격"을 따르도록 정확히 구현. 지정가·시장가 두 주문 유형을 모두 지원. 초기 AI 코드의 체결가 오류(D-01)는 사람이 도메인 검토로 교정. | defect_log D-01, `_record_trade`, 전략 패턴 |
| **신뢰성** (결함 없음·오류 허용성) | 모든 입력을 `_validate_order_input`으로 검증해 잘못된 주문을 거부. 단위 테스트 41개·커버리지 100%로 동작 보장. 개발 중 결함 14건을 제거. | `test_orderbook.py`, defect_log |
| **사용용이성** (학습성) | Streamlit UI에 주문 폼·호가창·체결내역을 한 화면에 배치하고 색상·피드백을 일관되게 설계. | Design.md, `app.py`, 스크린샷 |
| **효율성** (시간·자원) | 메모리 기반 list 구조로 단순하나, 대량 주문엔 불리. 아키텍처 단계에서 list↔heap 트레이드오프를 명시적으로 검토하고 벤치마크로 검증. | architecture.md (ATAM), benchmark.md |
| **유지보수성** (분석·변경·시험용이성) | 책임을 메서드 단위로 분리하고, 주문 유형 차이를 전략 패턴으로 캡슐화(개방-폐쇄). MI A등급, 커버리지 100%로 변경 시 회귀를 즉시 탐지. | CODING.md, market_order_design.md, §3 메트릭 |
| **이식성** (설치용이성·재사용성) | 엔진(`orderbook.py`)은 외부 라이브러리 의존이 없는 순수 Python이라 어디서나 실행 가능. UI(Streamlit)와 엔진이 분리되어 엔진만 재사용 가능. | architecture.md (계층 분리) |

## 3. 품질 메트릭 측정


### 3.1 구현 메트릭

| 메트릭 | 측정값 | 도구 |
|---|---|---|
| LOC (전체 줄 수) | 282 | radon raw |
| SLOC (순수 코드 줄) | 147 | radon raw |
| **사이클로매틱 복잡도(평균)** | **2.35 (A등급)** | radon cc |
| 최대 복잡도 메서드 | `_match` = 9 (B), `_validate_order_input` = 9 (B), `cancel_order` = 5 (A) | radon cc |

![메서드별 사이클로매틱 복잡도](../reports/quality_complexity.png)

사이클로매틱 복잡도는 **"프로그램을 통과하는 독립 경로의 개수이며, 필요한 테스트의 횟수"**로 정의한다. 이 정의에 따르면 `_match`(복잡도 9)는 독립 경로가 9개이므로 최소 9개의 테스트가 필요하다. 실제로 체결 로직(`_match`)을 거치는 테스트는 체결·우선순위·상태·시장가·통합 클래스에 걸쳐 충분히 많아 복잡도가 요구하는 테스트 수를 충족한다. 한편 `_validate_order_input`은 시장가 주문을 추가하며 주문 유형 검증 분기가 늘어 6에서 **9로 상승**했고, 입력 검증 테스트(지정가·시장가·잘못된 유형)로 모두 커버된다.

### 3.2 설계 메트릭 (객체지향)

복잡도·결합도·응집도를 객체지향 형태로 구체화해, 클래스별로 측정했다.

| 클래스 | WMC (메서드 복잡도 합) | CBO (결합 클래스 수) | 응집도(LCOM) |
|---|---|---|---|
| Order | 2 | 0 | 단일 책임(데이터) |
| Trade | 2 | 0 | 단일 책임(데이터) |
| MatchingStrategy | 2 | 0 | 인터페이스 |
| LimitStrategy | 2 | 1 (MatchingStrategy) | 단일 책임(지정가 규칙) |
| MarketStrategy | 2 | 1 (MatchingStrategy) | 단일 책임(시장가 규칙) |
| OrderBook | 35 | 2 (Order, Trade) | 단일 연결(높음) |

해석:
- **WMC**: 복잡도가 `OrderBook`에 집중(35)되고 데이터·전략 클래스는 2로 낮다. 매칭 엔진이 핵심 책임이므로 의도된 분포이며, 시장가 추가에도 OrderBook의 WMC가 33→35로 소폭만 올랐다(전략으로 분리한 효과).
- **CBO(결합도)**: `LimitStrategy`·`MarketStrategy`가 `MatchingStrategy`에 결합(1)된 것은 **상속 관계**라 의도된 것이다. `OrderBook`은 Order·Trade 2개에만 결합되고, `Trade`는 여전히 **0**(주문을 ID로만 참조하는 약결합)이다.
- **응집도(LCOM)**: 각 전략 클래스는 한 가지 주문 유형의 규칙만 담아 응집도가 높다. `OrderBook`의 메서드는 호가창 상태나 메서드 호출 관계로 연결되어 하나의 덩어리를 이룬다.

### 3.3 시스템 메트릭 (신뢰도)

강의록의 신뢰도 메트릭은 **MTBF = MTTF + MTTR**(고장 사이 평균 시간)이다. 그러나 MTBF는 **운영 중 실제 고장 데이터**가 있어야 계산할 수 있는데, 본 시스템은 운영 이력이 없는 학습용 시뮬레이터라 직접 측정이 불가능하다.

따라서 무리하게 만들지 않고 **대리 지표**로 신뢰도를 평가한다.

| 대리 지표 | 값 | 의미 |
|---|---|---|
| 개발 중 발견·제거 결함 | 14건 | 출하 전에 잡아낸 결함의 양 |
| 테스트 통과율 / 커버리지 | 41개 전부 통과 / 100% | 잔존 결함이 억제됨 |
| 입력 검증으로 거부되는 비정상 입력 | 7종 + 시장가 가격 지정·잘못된 유형 | 오류 허용성 확보 |

### 3.4 유지보수성 지수 (MI)

`radon`이 산출하는 종합 유지보수성 지수(Maintainability Index)는 **55.56 (A등급)**이다. 시장가 주문 추가로 코드가 늘어 58.98에서 소폭 내렸으나 여전히 A등급("유지보수가 용이함")을 유지한다.

## 4. 메트릭 종합 해석

| 항목 | 측정값 | 일반 권장 기준 | 
|---|---|---|---|
| 사이클로매틱 복잡도(평균) | 2.35 | 10 이하 권장 | 
| 최대 복잡도(`_match`·`_validate_order_input`) | 9 | 10 초과 시 분리 권장 | 
| 테스트 커버리지 | 100% | 80% 이상 권장 | 
| CBO(최대) | 2 | 낮을수록 좋음 | 
| 유지보수성 지수 | 55.56 (A) | A등급 양호 | 

이제 `_match`와 `_validate_order_input` 두 메서드가 복잡도 9로 권장 상한(10)에 근접한 경계 항목이다. 특히 `_validate_order_input`은 시장가 주문 검증이 더해지며 올랐다. 지금은 분리하지 않되, 주문 유형이 더 늘어 둘 중 하나라도 10을 넘으면 헬퍼로 분리하기로 한다(유지보수 문서의 개선 항목과 연결).

## 5. 프로세스 성숙도 관점 (CMMi)

 본 프로젝트를 CMMi 개념에 빗대면 다음과 같다.

- 단계와 산출물이 **정의**되어 있고 문서로 남는다(process·SRS·Design…) → "정의된 프로세스" 수준을 흉내 냄.
- 품질을 **숫자로 측정**하고, 기능 추가(시장가) 전후로 재측정해 변화를 추적한다 → "정량적으로 관리되는 프로세스"의 입구.

1인 학습 프로젝트에 CMMi를 본격 적용하는 것은 과하므로, 여기서는 개념만 차용해 "우리 프로세스가 어느 수준인지"를 가늠하는 데 그친다.
