## 0. 본 문서의 목적

바이브코딩으로 개발하는 동안 AI가 만든 결함을 모두 모으고, 각 결함을 어느 단계에서 어떤 방어선이 잡았는지 추적한다. 이는 "프로세스가 AI 산출물의 빈틈을 잡는다"는 주장을, 일화가 아니라 표와 숫자로 뒷받침하기 위한 자료다. 결함은 코드 버그뿐 아니라 요구·설계 단계의 누락·오류까지 포함한다.

## 2. 결함 로그

| ID | 단계 | AI가 만든 결함 | 심각도 | 발견 메커니즘 | 조치 |
|---|---|---|---|---|---|
| D-01 | 요구 분석 | 체결가를 어느 주문 가격으로 정할지(먼저 호가창에 있던 주문 기준) 규칙 누락 | 치명적 | 사람 도메인 지식 | 도메인 규칙을 사람이 명세해 SRS에 반영 |
| D-02 | 요구 분석 | 부분 체결 불변식(체결량 + 잔량 = 원주문량) 누락 | 높음 | 사람 도메인 지식 | 불변식을 요구사항·테스트로 명시 |
| D-03 | 요구 분석 | 다단계 매칭(한 주문이 여러 호가 체결) 시나리오 누락 | 높음 | 사람 도메인 지식 | 시나리오 추가, 통합 테스트로 검증 |
| D-04 | 설계 | 호가창 저장 구조로 Heap 추천 — 잦은 취소에 비효율(임의 삭제 O(n)) | 높음 | 사람 도메인 지식 | 취소 맥락 고려해 list 채택(ATAM 근거) |
| D-05 | 요구 분석 | Order에 userId 추가 — 단일 사용자 스코프 위반 | 중간 | 사람 도메인 지식 | 필드 제거, 스코프 재확인 |
| D-06 | 요구 분석 | 테스트가능성·추적성·페르소나 누락(과제 목적 미반영) | 높음 | 프로세스 절차 | NFR·추적성·페르소나를 SRS에 추가 |
| D-07 | 설계 | 부분 체결 시퀀스에서 잔량을 매칭 전에 등록(잘못된 흐름) | 높음 | 프로세스 절차 | 흐름은 사람이 정의, AI는 Mermaid 변환만 |
| D-08 | 구현 | 매칭 로직이 한 함수에 길게 뭉침(책임 미분리) | 중간 | 프로세스 절차 | 헬퍼 메서드로 분리(단일 책임) |
| D-09 | 구현 | 자바식 명명을 그대로 쓰면 PEP 8 위반 소지 | 낮음 | 자동화 도구 | snake_case로 변환 |
| D-10 | 구현 | 리팩토링 중 잔량 갱신 순서가 바뀌어 부분 체결 결과 1 오차 | 치명적 | 자동화 도구 | 단위 테스트로 발견 즉시 수정 |
| D-11 | 구현 | 미사용 메서드(예: get_best_bid) 데드코드 잔존 | 낮음 | 자동화 도구 | 제거 |
| D-12 | 테스트 | 성공 경로(happy path) 위주로만 테스트 생성 | 중간 | 프로세스 절차 | 동등 분할·경곗값 케이스 추가 |
| D-13 | 테스트 | 상태 기반 테스트 누락 | 중간 | 프로세스 절차 | 주문 상태 전이 테스트 추가 |
| D-14 | 테스트 | 테스트는 통과하나 매수 호가 삽입 정렬 루프 미커버(99%) | 중간 | 자동화 도구 | 케이스 추가해 100% 달성 |

## 4. 핵심 발견 — 다층 방어 (Defense in Depth)

세 방어선이 서로 다른 종류의 결함을 잡았다. 어느 하나만으로는 일부만 걸러졌을 것이다.

1. **도메인 결함은 사람만 잡았다 (D-01~05)**
   체결가 규칙·부분 체결 불변식·다단계 매칭·Heap 오추천·스코프 위반은 모두 사람의 도메인 지식이 잡았다. AI는 자기가 모르는 도메인의 빈틈을 스스로 발견하지 못한다. 특히 D-01(체결가 규칙)은 치명적인데, AI 단독이었다면 끝까지 누락됐을 결함이다.

2. **회귀·미검증 경로·데드코드는 도구만 잡았다 (D-10·14·11)**
   리팩토링 회귀(D-10, 부분 체결 1 오차)와 커버리지 빈틈(D-14, 99%)은 사람 눈으로는 발견하기 어렵다. AI가 짠 테스트가 "모두 통과"해도, 커버리지 도구가 숫자로 미검증 경로를 짚어 주었다. D-10 역시 치명적 결함인데 자동 테스트가 없었다면 런타임에야 드러났을 것이다.

3. **"원칙 미준수"는 프로세스 체크리스트가 잡았다 (D-06·07·08·12·13)**
   과제 목적 누락·시퀀스 환각·책임 미분리·happy path 편중·상태 테스트 누락은, 강의록 기준과 산출물을 대조하는 절차가 잡았다. AI는 "동작하는 것"은 잘 만들지만 "원칙에 부합하는지"는 잘 챙기지 못한다.

> **두 치명적 결함(D-01·D-10)이 서로 다른 방어선(사람 / 도구)에서 잡혔다는 점**이 핵심이다. 단일 방법으로는 이 둘을 동시에 막을 수 없었다.

## 5. 가정 분석 (프로세스가 없었다면?)

순수 바이브코딩(프로세스 미적용)을 가정하면:

- **사람의 도메인 검토가 없었다면** → D-01~05의 5건이 그대로 산출물에 남았을 것이다(체결가 오류 포함).
- **강의록 기준 대조 절차가 없었다면** → D-06·07·08·12·13의 5건이 누락·잔존했을 것이다.
- **자동 도구를 돌리지 않았다면** → D-10·11·14 등은 발견되지 못한 채 잠복했을 것이다.

즉 **14건 중 최소 10건(도메인·프로세스 영역)은 프로세스가 없었으면 그대로 통과**했을 가능성이 높고, 그중 둘은 치명적이다. 이것이 "프로세스에 입각한 바이브코딩"의 구체적 효과다.
