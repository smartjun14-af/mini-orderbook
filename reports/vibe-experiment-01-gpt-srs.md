# [실험 01] AI(GPT) 단독 생성 SRS 원본
   
   > 본 문서는 요구사항 분석 단계에서 AI에게 통째로 위임하여 생성된 SRS 원본이다.
   > [원본](./gpt-generated-srs.md)

   ---
요구사항 명세 단계에서 두 가지 방식을 비교 실험하였다. 첫째는 AI(GPT)에게 "미니 호가창/매칭 엔진 시뮬레이터의 SRS를 작성하라"고 통째로 위임한 경우이고, 둘째는 도메인 규칙을 사람이 먼저 정의한 후 AI에게 정제를 맡긴 경우다.
AI 단독 생성 SRS는 형식적으로는 완성도가 높았다. 개요, 범위, 용어 정의, 데이터 모델, 자료구조 설계까지 포괄적인 구조를 갖췄고, 예외 처리 표와 동작 시나리오도 포함되어 있어 첫인상은 전문적이었다.
그러나 도메인 깊이에서 결정적 결함이 발견되었다. 가장 중요한 것은 매칭 시 체결가를 어느 쪽 가격으로 결정하는가(passive order 기준)라는 핵심 규칙이 누락된 점이다. 이는 매칭 엔진의 본질에 해당하는 규칙으로, 이것이 모호하면 구현 단계에서 체결가 산정 버그로 직결된다. 또한 부분 체결의 검증 가능한 불변식(체결량 + 잔량 = 원 주문량)과 다단계 매칭(multi-level matching) 시나리오도 빠져 있었다.
AI는 자료구조 측면에서도 함정을 드러냈다. 호가창 저장 구조로 Max Heap / Min Heap을 추천했으나, 이는 주문 취소(임의 원소 삭제)가 빈번한 본 시스템에서 비효율적이다. Heap은 임의 원소 탐색·삭제가 O(n)이기 때문이다. 교과서적 정답을 제시했을 뿐, 취소 기능과의 상호작용이라는 시스템 맥락은 고려하지 못했다.
AI는 요구하지 않은 범위를 임의로 확장하기도 했다. Order 객체에 userId 필드를 추가하여 다중 사용자 시스템을 암시했는데, 이는 본 프로젝트가 의도적으로 단일 사용자 학습용으로 한정한 스코프와 충돌한다.
가장 본질적인 한계는 이 과제의 목적 자체를 AI가 인식하지 못했다는 점이다. AI가 생성한 SRS에는 테스트가능성 요구사항(커버리지, 상태 기반 테스트), 요구사항 간 추적성(FR↔US↔NFR), 사용자 중심 설계 요소(페르소나, user story)가 전무했다. AI는 "SRS는 이런 형식이다"라는 일반적 패턴을 재현했을 뿐, "소프트웨어 공학 프로세스 적용을 검증한다"는 본 과제의 맥락은 반영하지 못했다.
결론적으로, 요구사항 분석 단계에서 AI는 '형식의 보조자'로서는 유용했으나 '도메인의 정의자'가 될 수는 없었다. 도메인 규칙(가격-시간 우선, 체결가 결정, 부분 체결 불변식)을 사람이 명세한 후 AI에게 정제를 위임했을 때 비로소 정합성 있는 SRS가 완성되었다. 이는 바이브코딩이 프로세스의 통제 없이 적용될 경우, 그럴듯하지만 핵심이 빠진 산출물을 양산할 수 있음을 보여준다.
